## 1. idea 的五个论点逐条核验

### 1.1 「视图树是 ground truth，像素层面三义性不可消解」✅ 成立

「两个图标堆叠」的三义性（布局 bug / 设计性叠加 / 动画中间帧）是架构常识，代码层面无对应物可验。视图树含系统维护的坐标与层级（dump XML 每节点带 bounds——解析先例 common.py:1393, :1604-1611）。**接受为设计前提。**

### 1.2 「采集端要加 uiautomator dump，外部改造项」❌ 已存在，无需改造

`capture()`（common.py:1350）的采集管线：

```python
with stage("screenshot"):  shot = d.screenshot()      # :1357
with stage("png_save"):    shot.save(png)             # :1359
with stage("ui_dump"):     xml_text, attempts = _dump_hierarchy(d, xml)  # :1361
...
with stage("meta_save"):   meta.write_text(...)       # :1383
```

png / xml / meta 三件套由 `evidence_paths()`（common.py:1036）产出**同一证据目录**，原子配对。idea 提的「与截图同触发点异步落盘、分析阶段按时间戳配对（scene_matcher）」**是多余设计——配对机制天然存在**。

### 1.3 「dump 耗时 1~3s，量产会拖采集节奏」❌ 实测不成立（数据验证）

storage 现有 10 份 meta.json 的 `timing.stages_ms` 实测（4K 屏 3840×2560）：

| 阶段 | n | 中位 | 均值 | min | max |
|---|---|---|---|---|---|
| ui_dump | 10 | **160ms** | 159ms | 116ms | 194ms |
| screenshot | 10 | 383ms | 398ms | 317ms | 569ms |
| png_save | 10 | 516ms | 516ms | 205ms | 867ms |

dump 比截图还便宜；整个采集最贵的反而是 png_save。**同步计算可接受，无需异步化**。

### 1.4 「ANR/卡死时刻 dump 可能失败，只能作增强证据」✅ 成立，且已有工程兜底

`_dump_hierarchy` 返回 `dump_attempts`，>1 时 `capture()` 留痕（common.py:1377-1378「留痕：这次是清理残留后救回来的」）——dump 失败/重试是**本仓库已实测发生过**的场景。设计里「dump 失败 → 信号缺席 + 留痕」是既有行为，不是新风险。

### 1.5 「Toast/悬浮球/PopupWindow/角标要白名单」⚠️ 方向对，对象错一半

- **Toast 不在 dump 树里**（Toast 是系统层窗口，uiautomator 的 accessibility 树通常不含它）——不存在「误报 Toast」问题，白名单条款应删；
- 真正需要豁免的是：**合法父子包含**（子矩形含于父矩形是布局常态，不算堆叠）、**PopupWindow/Dialog 类跨层容器**（按 class 判断）、**角标类 rid**（resource-id 含 badge/dot 的节点）；
- idea 说「悬浮球本来就该跨层叠加」成立，按 class/package 豁免。

### 1.6 「融合三规则」✅ 成立，但落点要改

本仓库没有「Phase2a/2b 融合层」。真实判图路径是：**对话 AI 自己看截图判语义**（vision.py:4「v2 默认由对话 AI 自身判图；本工具用于批量回放等无对话场景」），纪律由 SKILL.md 约束。所以三规则的落点是：

| idea 里的融合层 | 本仓库的实际落点 |
|---|---|
| 算法层产出「真实堆叠」信号 | `capture()` 内新增计算，信号**落 meta + 事件流，不回传 AI**（同 sig/timing 的处理，observe.py:152-155「落盘、不回传」是仓库既有惯例） |
| Phase2a/2b 确定性证据注入 | observe/act 的 payload 按需携带：检测到堆叠时给一行摘要 + 明细工具指引 |
| 融合规则 | **SKILL.md 新增纪律节**（AI 判「堆叠」必须双源核对；树否认 → 降级为设计性叠加；树报而 AI 没报 → 补报义务） |

## 2. 现状架构（设计的事实地基）

```
一次采集（observe 或 act 后取证）
  └─ capture(d, png, xml, meta)          common.py:1350
       ├─ d.screenshot()                  → shot.png
       ├─ _dump_hierarchy(d, xml)         → dump.xml  ← UI 树（含每节点 bounds）

  screen_view(xml) → nodes/texts/next → AI 每步读的「可点清单」
```

## 3. 方案设计

### 3.1 拓扑（改什么、不改什么）

```
capture() ──► _dump_hierarchy ──► [新增] layout_check.scan(xml_text, fg_package)
                                        │  纯函数：解析可见叶子 → 两两矩形关系 → 信号列表
                                        ├─ 命中 → meta.json 增 "layout" 块 + 事件流 info 增 overlap_count
                                        └─ 未命中/解析失败 → 无痕（不加字段）
observe/act payload                     [新增] overlap_count > 0 时带一行摘要 + 指引
                                          "layout_overlap: 2 处（详情 android_layout_check）"
[新增工具] android_layout_check          按需读指定证据目录的 dump.xml，返回明细
SKILL.md                                [新增] 堆叠判定三规则（纪律层）
```

**不改**：判定层（仍由 AI 裁决）、存储 schema（信号随事件流走）、视觉通道（vision.py 不动）。

### 3.2 检测器规格（tools/layout_check.py）

```
scan(xml_text, fg_package, screen_size) -> {overlaps: [...], scanned: n, skipped: reason?}

输入过滤（复用既有约定）：
  - 按前台包过滤（同 summarize_xml :1553-1559 的语义与回退理由）
  - 只取叶子节点（无子 node 的 <node>）：容器矩形重叠是布局常态
  - 零尺寸/屏幕外 bounds 剔除（x1>=x2 或越出 screen_size）
  - class / resource-id 豁免表（PopupWindow 容器、badge 类 rid；表可配置）

判定规则（两两配对 a,b，均为叶子）：
  - 父子包含豁免：b 在 a 的祖先链内 → 跳过（祖先信息解析时顺手带上）
  - 交集面积 / 较小矩形面积 > CONTAIN_RATIO(0.8) 且非祖先关系 → "contained" 型堆叠
  - IoU > IOU_THRESHOLD(0.3) → "overlap" 型堆叠
  - 产出：{a: {class,rid,center}, b: {...}, kind, iou, inter_ratio, bounds}
```

复杂度：可见叶子 n≈300（summarize_xml 的 max_nodes 同量级），两两 ~4.5 万对，纯 Python **毫秒级**；加上解析约 **<20ms**，相对 ui_dump 160ms 不可见。

### 3.3 参数与阈值

| 参数 | 初值 | 依据 |
|---|---|---|
| IOU_THRESHOLD | 0.3 | 起步值【待验证】——用真实页面跑一周，按误报样本回调 |
| CONTAIN_RATIO | 0.8 | 小矩形被大矩形吞 80% 以上才算"压住" |
| 豁免表 | 空（先裸奔收误报） | 先看真实误报长什么样再定豁免规则，避免拍脑袋白名单漏掉真异常 |

**明确反对 idea 的「先建白名单」顺序**：白名单应该由误报数据驱动，而不是预设。第一批裸跑的误报本身就是标注数据。

### 3.4 融合规则（落 SKILL.md，节选设计）

> ### ⚠️ 「堆叠/遮挡」类判定必须双源核对
> 你看到的截图和 `android_env/observe` 返回的 `layout_overlap` 信号是两个独立证据源：
> 1. **你判堆叠 + 信号实锤** → 高置信布局异常，finding 引用该步 event_id，注明两源一致；
> 2. **你判堆叠 + 信号否认** → 大概率是设计性叠加（角标/悬浮层）或动画帧，不要判 FAIL；要翻案必须调 `android_layout_check` 看明细（谁压谁、什么控件）；
> 3. **信号报了 + 你没看出** → 你漏了，必须看明细并补判——`layout_overlap` 出现在 payload 里就是强制检查项。
> 视图树拿不到（dump 失败 / 自绘内容）时退回纯视觉判定，且 finding 必须注明「仅单源」。

### 3.5 数据流（一次典型判定的证据链）

```
AI 截图直觉「两个按钮叠了」
  → observe payload 已带 layout_overlap: 2 → AI 调 android_layout_check
  → 返回 [{A:Button"开始" , B:Button"取消", kind:overlap, iou:0.42, ...}]
  → AI 裁决：两个同级可点按钮互相压住 = 功能受损 → FAIL finding
  → finding 引用：observe 的 event_id + layout_check 的 event_id（双证据）
```

---

### 3.6 设计决策记录：为什么常驻采集而不是「走视觉检查时才调用」

评审时提出过替代方案：只在 AI 做视觉检查时调用。不采纳，理由：

1. **常驻是三规则第 3 条（AI 漏检补报）的唯一实现方式**。按需调用只能当"确认器"——AI 先起疑才有信号，永远兜不住"AI 压根没注意到"的原始痛点；
2. 成本已被实测消解：dump 本来就发生（160ms），扫描增量 <20ms/步（一条 30 步用例 <0.6s），未命中时对 AI 上下文零字节；
3. 对 AI 的注意力占用本来就只在命中时发生（payload 一行摘要），"视觉检查相关时才打扰"的效果已经内嵌；
4. 不能挂 android_vision：它是批量回放/无对话场景的可选通道（vision.py:4），v2 默认判图者是对话 AI 自身，多数判定不经过该工具；
5. 降级路径保留：误报噪音大时可关闭常驻计算退回按需模式（env 开关），但必须先裸跑一周——阈值与豁免表要误报数据驱动（见 3.3）。

## 4. 评估

### 4.1 收益

- 把「堆叠」从 AI 猜测题变成双源验证题——误报（角标被当成 bug）与漏报（AI 没注意到）两头都收；
- 信号随既有事件流走，**findings 可绑定确定性证据**（符合仓库「证据绑定」纪律，vision.py:99-110 的事故教训同理）；
- 零新增采集成本（dump 本来就发生）。

### 4.2 成本

| 项 | 量 |
|---|---|
| layout_check.py | ~150 行 |
| capture 挂点 | ~20 行（common.py） |
| observe/act payload 摘要 | ~10 行 × 2 |
| android_layout_check 注册 | ~60 行（lib/index.js，照 android_read_file 模式） |
| SKILL.md 纪律节 | ~30 行 |
| **合计** | **~270 行，1 人日** |

### 4.3 风险与坑（修订版，替代 idea 的四坑）

| # | 风险 | 状态 | 处置 |
|---|---|---|---|
| 1 | ANR 时刻 dump 失败 | ✅ 代码已证实且有兜底（common.py:1377） | dump 失败 → 信号缺席即信息（"此刻树拿不到"本身留痕）；纪律要求单源 finding 注明 |
| 2 | 自绘内容不在树（SurfaceView/Canvas/WebView 未开 accessibility） | ✅ 成立 | 不处理——这类归 AI 视觉判，双源规则第 1 条天然覆盖 |
| 3 | 白名单误报爆炸 | ⚠️ 修正 idea：Toast 不在树里；真风险是父子包含与弹窗容器 | 父子豁免写进算法；其余豁免由误报数据驱动（3.3 节） |
| 4 | dump 耗时 | ❌ 实测证伪（160ms 中位） | 无需异步化，同步计算 |
| 5 | **截图与 dump 的时序差**（screenshot 先于 dump ~550ms，动画帧两源不一致） | ⚠️ 新发现，idea 未提 | 不修——两源不一致恰恰是三规则要消化的情况；强行同步会破坏 capture 的 rotation 判定依赖（截图先行的顺序有 exist reason，common.py:1357-1364）。标注【待验证】：上线后统计「信号否认 AI」案例中动画帧占比 |
| 6 | payload 膨胀 | 新发现 | 摘要一行 + 明细按需，符合仓库「nav 62→9 节点省 93%」的压缩文化 |

### 4.4 结论分级

**必须**
1. 检测器纯函数化（输入 xml_text 输出信号）——可独立单测；
